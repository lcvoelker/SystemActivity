== Observations / possible follow-ups (ask before doing any that change volume) ==
- Windows often reports 2 WRITE events per save (truncate + write), so write counts run ~2x
  the number of saves. Could debounce WRITEs per file within ~100 ms.
- Atomic-save editors (JetBrains "safe write", MS Office, Vim with some settings) save via
  temp file + rename, which reads as CREATE/RENAME/REMOVE and pushes sessions toward
  "organization". Office lock files (~$name.docx) and `name~` backups aren't filtered yet.
- Heartbeat option for kill recovery: update sessions.last_seen_at at each 5-min save so an
  orphan's end time is accurate even with no recent activity.
- Pre-existing gofmt issues in internal/filter/ignore.go (not touched).

  %LOCALAPPDATA%\filemaster\unsaved\unsaved-<nanos>-<pid>.json (temp + rename). The next
  watcher claims files by renaming them, drops entries past retention or whose session is gone
  (those would poison every save), and merges the rest into its buffer; they go out with the
  next regular save. Corrupt files are kept as .bad. A killed process still can't spill.

(the daemon runs as DML-only fm_app; auto-migrating would need owner credentials in the
daemon and would run destructive migrations like 00002 without review).
Known gap (asked owner): if a watcher's final save AND EndSession both fail, the next start
closes that session as an orphan before the recovered entries are saved, so it gets
kind "other" and a 0s duration. Fix would be saving recovered entries immediately at startup
(an extra save → needs owner approval) or reclassifying after the recovered save.
