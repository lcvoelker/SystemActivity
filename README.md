# SystemActivity (filemaster)

A Go daemon that watches a large folder tree during a work session, records
only the files that change while it runs, and classifies each session as
**work** (frequent saves), **organization** (creating, renaming, moving and
deleting files and folders) or **other**. Activity goes to PostgreSQL with
content-addressed version history, so you can ask when a file's *content*
actually changed and which other paths hold identical content. Data is kept
for 3 days.

- **Watcher**: recursive `fsnotify` watch with rename pairing; ignores folder
  writes and touches to files that weren't modified during the run
- **Sessions**: split by an inactivity timeout (default 5 min), classified on close;
  sessions left open by a killed watcher are closed on the next start
- **Storage**: `pgx` pool, type-safe queries generated by `sqlc`, embedded
  `goose` migrations, per-file merging saved every 5 minutes via `COPY`
- **Security**: separate owner and app roles; the daemon can't change the schema

## Setup

1. One-time database setup as a superuser (creates the `filemaster` schema,
   roles if missing, default privileges and the `btree_gist` extension):

   ```
   psql -h localhost -U postgres -d filemaster -f db/bootstrap.sql
   ```

2. Copy `.env.example` to `.env` and fill in the `fm_app` / `fm_owner` passwords.

3. Apply migrations as the schema owner:

   ```
   go run ./cmd/filemaster migrate up
   ```

## Usage

```
go run ./cmd/filemaster watch D:\Downloads\look   # type "end" or Ctrl+C to stop
go run ./cmd/filemaster sessions -n 10            # recent sessions: kind and per-op counts
go run ./cmd/filemaster history D:\Downloads\look\notes.txt
go run ./cmd/filemaster prune                     # apply the 3-day retention now
go run ./cmd/filemaster migrate status
```

`watch -offline` prints events without a database.

## Database design

All objects live in the `filemaster` schema, never `public`.

| Table | Purpose |
|---|---|
| `sessions` | One row per burst of activity (host, root, start/end, `kind`) |
| `files` | Every path that changed, stored once |
| `blobs` | Content-addressed: one row per distinct SHA-256 |
| `file_activity` | One row per file per 5-minute window with operation counts, **range-partitioned by day** |
| `file_versions` | Which blob each path held over time, `[valid_from, valid_to)` |
| `session_summary` | View: kind, event counts and unique files per session |

Design choices worth knowing:

- **No overlapping versions**: `file_versions` has an `EXCLUDE USING gist`
  constraint on `(file_id, tstzrange(valid_from, valid_to))`, so the database
  itself guarantees a file never has two versions at the same time.
- **Least privilege**: `fm_app` only has `SELECT/INSERT/UPDATE/DELETE`, granted
  through `ALTER DEFAULT PRIVILEGES`. Daily partitions and retention run
  through `SECURITY DEFINER` functions owned by `fm_owner`, so the app never
  needs DDL rights. `migrate` refuses to run as anyone but the schema owner.
- **Bounded memory**: events are merged per file in memory (a file saved
  40 times is one entry with a write count) and hashed once at save time.
  At most 1,000 entries are held; reaching that saves early. Sessions keep
  only counters. Folder watches use 16 KB buffers instead of 64 KB.
- **Batched writes**: every 5 minutes, one transaction does path and blob
  upserts using arrays, the activity rows via `COPY`, then version changes as
  one pipelined batch. If the database is down, data waits for the next save.
- **Retention**: data older than 3 days is removed at startup and hourly,
  mostly by dropping whole daily partitions.

## Development

```
go install github.com/sqlc-dev/sqlc/cmd/sqlc@v1.29.0
sqlc generate          # after editing internal/db/queries or migrations
go test ./...          # storage integration tests run when FILEMASTER_TEST_DATABASE_URL is set
```

Integration tests delete data older than 3 days, so point
`FILEMASTER_TEST_DATABASE_URL` at a disposable database (see AGENTS.md).
